# 2. The LLM gate decides from severities, not from the model's verdict

- Status: accepted
- Date: 2026-10-15

## Context

An LLM review can block merges only if its outcome is predictable enough to trust and cheap enough
to run on every PR. Asking the model "should this merge?" gives a verdict that shifts with wording
and can be talked into passing by text in the diff itself. Models also refuse, time out, or return
truncated output, and the gate has to say what happens then.

## Decision

- The model returns structured findings only (`Review`: summary plus findings with a severity from
  a rubric written into each prompt). `llm-gate` computes the verdict in code.
- Each check in `tools/llm-gate/checks.yaml` is **blocking** (fails when a finding is at or above
  `fail_on`) or **advisory** (reports, never fails). Today `code-review` blocks on `high` and
  `security-review` on `medium`; everything else is advisory.
- Blocking checks **fail closed**: an API error, refusal, truncated or missing output, or a diff over
  `max_diff_kb` fails the check (exit 2) unless the check sets `on_error: pass`.
- A human can override blocking findings with the `llm-override` PR label (write access needed).
  The findings are still reported.
- **Amended 2026-10-18: a diff over the size cap is overridable; other errors are not.** A
  **generated** file whose own diff is over `max_file_kb` (64 by default) is left out of what the
  model sees, and named in the PR comment, the audit record and the release attestation, with the
  list given to the reviewer as well. Generated code (gRPC stubs, EF Core migrations, SQL seed
  data) would otherwise crowd the hand-written part of a change out of `max_diff_kb`, or push the
  whole diff over it, and a PR carrying such a file had no way through the gate but editing the
  gate. Three things keep that from becoming a way through: a file is left out only if it both
  matches `trimmable_paths` **and** carries a generator's marker (`<auto-generated`,
  `Code generated by`, ...) near the top, so a hand-written file padded past the cap stays under
  review; a **blocking** check reviews a diff with anything missing only when the PR carries an
  honoured override, so every partial blocking review has a human reason on the audit log; and the
  diff is fetched one file at a time, so a quoted or awkward path cannot be swallowed into a
  trimmed file's chunk. An advisory check trims and reports, since it blocks nothing.
  **The limit:** the override is PR-wide, as it has always been, so one accepted for findings on
  one check also permits a partial review on another. The attestation lists every omitted file per
  check, which is where that shows up. If the trimmed diff is still over `max_diff_kb`,
  the `llm-override` label plus its `/llm-override <reason>` comment accepts it **unreviewed**:
  the verdict stays `error`, the exit code becomes 0, and the record carries
  `override_honoured`. An API error, refusal, truncated output or a crash stays non-overridable:
  a gate that broke or refused is not an approval, and a re-run is the answer. The metrics count
  unreviewed overrides apart from overridden findings.
- Prompts are files in `.claude/commands/llm-<check>.md`, shared with interactive Claude Code, and
  treat the diff as untrusted data. They are reviewed like code.
- Two engines sit behind one interface: the Messages API (diff inline, one request) and the Claude
  Agent SDK (the same prompt with read-only tools in the repository; originally run as a slash
  command, superseded by [ADR 0004](0004-gate-tooling-from-base-branch.md)). The check chooses one;
  `--engine both` and `llm-compare` exist to compare them.
- Results are cached by check, engine, model, prompt and diff, so re-running a PR without changes
  costs nothing.
- **Amended 2026-10-18: only unreviewable files are excluded.** `diff.EXCLUDES` dropped
  `*.g.cs`, `*.generated.cs`, `*.Designer.cs` and `*.min.js` by name, and the SDK compiles those
  into the app: a PR made only of them passed both blocking checks as "not applicable" and counted
  as reviewed (F010). What stays excluded is a resolved dependency graph (lock files) and this
  repository's own test data, neither of which a reviewer can judge. Generated code goes through
  the review, and its bulk is handled by the per-file size cap, which reports what it left out.
  A diff of nothing but excluded files now says which files those were, instead of reading like an
  empty diff.
- **Amended 2026-10-18: blocking reviews are not cached, and the diff is read with the base's
  attributes.** Actions caches are shared by every workflow run of the same ref, `pull_request`
  runs the PR's own workflow files, and the cache key is a sha256 of inputs the PR author knows
  (check, engine, model, the base's prompt, their own diff), so a sibling workflow the PR adds
  could save a findings-free result that `llm-review` would restore as a verified pass. An HMAC
  over the entry doesn't help: that workflow can read the same repository secrets. `llm-review`
  therefore keeps no review cache at all, and a re-run of an unchanged PR pays again (about $0.12
  for a high-risk PR). The collector refuses a blocking record that claims a cache hit. The triage
  cache stays: a forged entry there can only *raise* the model's risk, and the collector recomputes
  the floor anyway. Separately, the review diff is built with `git --attr-source=<base> … --text`,
  so the PR's own `.gitattributes` can no longer turn its files into "Binary files … differ"; a
  vendored binary is excluded by `diff.EXCLUDES`, which is code on the base branch.

## Consequences

- A prompt or rubric change can change verdicts; it goes through review like any other gate change.
- Fork and Dependabot PRs have no API key; the CI workflow (Phase 8) reports that instead of failing.
- The prompt files are named `llm-<check>` rather than `<check>` so they don't shadow Claude Code's
  built-in `/code-review` and `/security-review`.
- **What the gate skipped is on the record, never silent** (2026-10-18). A trimmed file and an
  accepted-unreviewed diff both reach the release attestation's `unreviewed` list, so "this
  release was reviewed" keeps meaning what it says. The collector enforces the pairing: a blocking
  check reporting `error` with exit 0 and no honoured override is a tamper event.
